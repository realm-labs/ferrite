**Transition and ordering:**

### Held placement transaction

Item use reads clicked position, clicked face, target position one block along that face, player
and held stack in that order. For a nonnull player, admission requires a horizontal clicked face
and `player.mayUseItemAt(target,face,stack)`; failure returns `FAIL` before entity construction.
A null-player programmatic context skips that admission. Paintings reject a later vertical
direction through their horizontal-only direction setter, while frames can represent all six
directions even though ordinary player placement admits only four.

Painting placement constructs a painting and copies every holder currently in
`#minecraft:placeable` into a candidate list. Empty tag returns `CONSUME`. It sets the requested
direction, then for every candidate temporarily sets that variant and evaluates full painting
survival. It removes failures, returns `CONSUME` if none remain, finds the greatest `width*height`
among survivors, removes every smaller-area candidate, and consumes exactly
`paintingRandom.nextInt(maximalCandidateCount)` to choose uniformly. It installs the winner,
reapplies direction and returns the entity.

Frame placement directly constructs the matching ordinary/glow subtype at target and direction.
All three paths then apply default stack configuration before the final survival test:
`custom_name` and `custom_data` implicit components apply generically, a painting's
`painting_variant` replaces the random winner, and matching typed `entity_data` loads under the
generic server/operator permission rule. This ordering has two consequences:

- even a preset painting first performs candidate survival tests and the maximal-candidate random
  draw; its component only then overrides the result;
- the configured result receives one final survival test, but a configured small variant cannot
  rescue a placement for which the live placeable candidates produced no survivor.

If final survival fails, use returns `CONSUME` without sound, game event, spawn or shrink. On
success, the server plays the subtype placement sound at volume/pitch `1`, emits `ENTITY_PLACE`
at entity position with the player as source, and offers the entity through `addFreshEntity`;
that Boolean result is ignored. Both logical sides then call `heldStack.shrink(1)` and return
`SUCCESS`. Server creative use wraps the call by saving and restoring the original count; client
prediction can shrink before authoritative inventory convergence.

### Hanging support, overlap and delayed removal

A painting's box is centered at attachment-block center, shifted `0.46875` opposite facing,
shifted `0.5` counterclockwise for even width and `0.5` upward for even height, and sized
`width x height x 0.0625` with the thin axis along facing. Survival first rejects block/world-border
collision in its pop box. Every block intersecting the rear support box must then be solid or a
diode. Finally, an intersecting hanging entity blocks the painting when it is another painting
regardless of direction or when it has the same direction regardless of subtype.

A nonfixed frame instead uses a `0.75 x 0.75 x 0.0625` pop/support box and checks only the single
block opposite its facing. That block must be solid; a diode is also accepted only for horizontal
frames. Its coexistence test rejects only an intersecting hanging entity with the same direction.
Thus ordinary/glow frames at different directions can coexist even when their boxes intersect,
whereas same-direction painting/frame or frame/frame pairs cannot. A displayed stack carrying
`map_id` expands the frame's visible/entity box to `1 x 1 x 0.0625`, but collision/support and
coexistence continue to use the `0.75` pop box. A fixed frame returns true before all collision,
support and coexistence checks.

Every server tick calls `checkBelowWorld`. A counter initialized to zero is compared through
`checkInterval++ == 100`; therefore the first and subsequent ordinary survival probes are 101
server ticks apart. A failed probe discards the entity, then invokes subtype drop behavior with a
null remover. Any nonzero server `move` vector or `push` vector likewise kills and drops a
nonfixed hanging entity; fixed frames ignore both. All are pickable. Player attack first respects
`level.mayInteract`; rejection consumes the attack, while admission submits zero-value
player-attack damage. A nonplayer attack uses the ordinary damage path.

The common damage path rejects base invulnerability and, when `mob_griefing` is false, a damage
source whose responsible entity is a `Mob`; otherwise it kills, marks hurt and drops once. The
common explosion wrapper ignores a water-submerged direct source and every explosion that does not
affect blocklike entities. `ENT-ENTITY-DROPS-001` owns the exact live `entity_drops`, infinite
materials, displayed-stack chance and map-cleanup branches.

### Painting destruction and pick behavior

With `entity_drops=false`, painting removal has no local break sound or item. With it true,
removal plays `entity.painting.break` at `1/1`; an infinite-material player suppresses the item,
and every other/null remover emits one default painting. Neither the drop nor middle-click result
retains the painting variant: pick always returns one default painting. Placement plays
`entity.painting.place` at `1/1`.

### Frame contents, rotation and comparator projection

Interaction with a fixed frame returns `PASS`. On the client, a nonfixed frame returns `SUCCESS`
when either it already has an item or the held stack is nonempty, and otherwise `PASS`, without
mutating authority.

On the server, an empty frame plus a nonempty hand first resolves map saved data. If present and
its current tracked-decoration count is strictly greater than `256`, interaction returns `FAIL`.
Otherwise `setItem` copies the hand stack with count one, recalculates the frame box, publishes
synced data, plays the subtype add-item sound at `1/1`, and notifies comparator neighbors. The
caller then emits `BLOCK_CHANGE`, consumes one through the living-entity ability rule, and returns
`SUCCESS`. A missing map record bypasses the limit, and a count exactly `256` still passes the
strict test.

When a nonempty frame is used, the held stack is irrelevant. The server plays the subtype rotate
sound at `1/1`, stores `(rotation+1) % 8`, notifies comparator neighbors, emits `BLOCK_CHANGE` and
returns `SUCCESS`. Normal rotations are `0..7`. An empty-hand/empty-frame server use returns
`PASS`. Slot zero exposes the displayed stack through `SlotAccess`; replacement still routes
through the one-count frame setter.

The frame analog value is zero when empty and `rotation % 8 + 1` otherwise, hence normal values
`1..8`. A comparator can use that value only after its first input is a redstone conductor and
the next one-block query box contains exactly one `ItemFrame`-class entity facing the comparator's
probe direction; zero or multiple matching frames suppress this entity source. Every item or
rotation change notifies output-signal neighbors at the attachment position.

A nonexplosion hit on a nonfixed frame with a displayed item removes only that item: it invokes
the shared drop helper with `dropFrame=false`, emits `BLOCK_CHANGE`, plays the subtype remove-item
sound and leaves the frame alive. Explosions skip this content-only branch. An empty frame or
explosion delegates to common hanging destruction. This item-pop branch precedes the common
`mob_griefing` check, so a mob source can clear displayed contents while that rule is false even
though it cannot then break the empty frame.

A fixed frame accepts damage only from a creative player or a damage type in
`#minecraft:bypasses_invulnerability`. Accepted damage delegates to common kill/drop, but the
private frame drop helper refuses both frame and displayed-stack itemization; outer break sound
and `BLOCK_CHANGE` still occur. Full ordinary removal emits the subtype frame item plus the
displayed stack according to `ENT-ENTITY-DROPS-001`. Middle-click returns a copy of the displayed
stack when nonempty; only an empty frame returns its ordinary/glow frame item.

### Maps, persistence and structure generation

A displayed stack is a framed map whenever it has `map_id`, even if saved map data is absent.
Every tenth server entity-tracker tick, a frame with a valid map record visits every player in the
level, calls the map carried/tracked update with this frame, and sends any resulting per-player
map update packet. Tracking-position maps add or refresh a frame decoration keyed by entity ID and
a frame marker keyed by block position. Killing a frame removes the marker before common kill.
Removing only displayed contents follows the cleanup asymmetries fixed by
`ENT-ENTITY-DROPS-001`.

Common hanging persistence stores `block_pos`. Painting additionally stores lowercase `facing`
through the legacy horizontal codec and its variant; missing facing defaults South and a missing
variant retains the registry-selected initial holder. Frames store optional `Item`, byte
`ItemRotation`, float `ItemDropChance`, uppercase six-direction `Facing`, `Invisible` and `Fixed`;
defaults are empty, `0`, `1.0`, Down, false and false. Frame load restores the item before
rotation/direction/flags. Direction and synced item/variant updates recalculate boxes. The
101-tick survival counter, in-flight placement attempt, candidate list/random draw, interaction
and drop transaction do not persist.

An End-city ship's `Elytra` data marker, when inside the current structure box and spawnable world
bounds, creates a normal item frame at the marker, faces it by rotating South with the piece,
sets one elytra without comparator notification, and offers it to the world. It does not use the
hanging item, survival test, placement event or placement sound, and ignores insertion failure.
Breaking that generated nonfixed frame is therefore a separate source of both an ordinary frame
and its elytra under the normal drop gates.

### Recipes, trades, tooltips and client projection

Painting's shaped recipe surrounds one `#minecraft:wool` with eight sticks. Item frame substitutes
one leather at center. Glow item frame is shapeless ordinary frame plus glow ink sac. Each emits
one default stack, discarding ingredient patches. Wool possession unlocks painting, leather
unlocks frame, and possession of either an ordinary frame or a glow ink sac unlocks glow frame;
direct recipe grant is also an alternative in every advancement.

The level-five shepherd record exchanges two emeralds for three paintings, maximum uses `12`,
villager XP `30` and reputation discount `0.05`. The level-four cartographer record exchanges
seven emeralds for one item frame, maximum uses `12`, XP `15` and discount `0.05`. No locked trade
emits a glow frame, and no nonstructure loot table directly emits any scoped item.

Painting hover text appears only when tooltip display permits `painting_variant`. A present
component emits optional title, optional author, then translated `width x height`; an absent
component emits gray `painting.random` only for a creative tooltip. Item/frame tooltips add no
special line.

Functional Blocks orders armor stand, item frame, glow item frame, default painting, then one
component-preset stack for every placeable variant before bookshelf. Presets sort by area and then
width, retaining registry order for equal keys. The operator tab similarly publishes the four
nonplaceable presets. Each identity has a direct item model.

Painting rendering uses the variant asset and emits one front/back/edge tile per block of width
and height, sampling packed light separately at every tile position. Frame rendering uses the
displayed stack in `FIXED` context and its rotation in 45-degree steps; a valid map uses the map
renderer instead. Invisible frames suppress only the frame model. Crosshair name projection
appears only with visible HUD and a displayed stack carrying a custom name, and uses that stack's
hover name.

A glow frame does not emit world light. Its entity renderer merely clamps sampled block light to
at least `5`; displayed nonmap items use packed light `15728880` and maps use `15728850`, while an
ordinary frame uses sampled light. The ordinary/glow sound families are respectively
`entity.item_frame.{place,break,add_item,remove_item,rotate_item}` and
`entity.glow_item_frame.{place,break,add_item,remove_item,rotate_item}`.

**Failure behavior:**

Permission failure returns `FAIL`; no painting candidate or failed final survival returns
`CONSUME`; neither shrinks or produces server effects. A failed entity insertion is ignored after
sound/event and still consumes in survival. Map count strictly above 256 returns `FAIL`; missing
saved data bypasses it. Fixed interaction passes and ordinary damage fails, while permitted
fixed-breaking produces no items. Failed End-city insertion is ignored. Invalid recipes, trade
offers and unlock criteria commit nothing.

**Persistence boundary:**

Items persist their generic components. Paintings persist attachment, direction and variant;
frames persist attachment, displayed stack, rotation, drop chance, direction, invisible and fixed
state. Map saved data separately persists decorations/frame markers and is repaired by tracking or
explicit cleanup. Data reload replaces painting variants, the placeable tag, recipes,
advancements and trades without replaying completed placement; resource reload replaces item,
painting and frame assets independently.

**Boundary cases and quirks:**

Preset painting placement still consumes random-selection work before component override. A larger
configured variant can invalidate an otherwise valid random placement, while a configured small
variant cannot run when no live candidate survived. Frame map contents enlarge rendering/entity
geometry but not the pop/support box. Different-direction frames can overlap; paintings conflict
with every painting regardless of direction. The survival comparison yields a 101-tick cadence,
not 100. Mob damage can pop frame contents before `mob_griefing` blocks frame destruction.
Exactly 256 tracked decorations still passes the strict limit. Rotation persistence uses Java
remainder rather than floor modulus, so malformed negative saved values are not normalized into
`0..7`. Painting drops/pick lose variant, filled-frame pick returns contents, and glow is a client
lighting treatment rather than a world light source.
