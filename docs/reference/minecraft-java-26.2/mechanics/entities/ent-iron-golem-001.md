**Authoritative state:**

Protocol entity ID `70` constructs `IronGolem` in `MISC`. Registration
fixes width/height `1.4×2.7`, no explicit eye height so the default
`2.7*0.85=2.295` applies, and client tracking range `10` with the default
update interval `3`. It declares no passenger attachment or riding offset
override and is **not** marked Peaceful-excluded, so it exists and behaves
identically on Peaceful.

`MISC` has maximum instances `-1`, is friendly and persistent, and uses
no-despawn/despawn distances `32/128`. Those distances are inert because
`AbstractGolem.removeWhenFarAway` returns `false`: an Iron Golem never
despawns for distance regardless of persistence flags or category. It also
contributes to no natural-spawn cap.

Attributes fix maximum health `100`, movement speed `0.25`, knockback
resistance `1`, attack damage `15` and step height `1`. Construction does
not raise the inherited `Mob` XP reward, so a killed Iron Golem drops
`0` experience. `decreaseAirSupply` returns its argument unchanged, so air
never falls and the golem cannot drown.

Inherited Entity, Living-Entity and Mob state occupies synchronized metadata
slots `0..15`. Iron Golem adds slot `16`, serializer ID `0` (`BYTE`),
default `0`, whose bit `0x01` is the player-created flag. No other bit is
used.

`PlayerCreated` persists as a boolean, default `false`. Neutral-mob anger
persists as `anger_end_time` (long) and nullable `angry_at`, with the legacy
`AngerTime` key still read. The attack-animation counter, the flower-offer
counter, the offer goal's target and tick, targets, active goals and all
client render state are transient. Slot `16` does not persist and is
restored from `PlayerCreated` on load.

Persistent anger uses `TimeUtil.rangeOfSeconds(20, 39)`, so a triggered
anger timer samples uniformly from `400..780` ticks.

**Transition and ordering:**

### Complete goal graph, targeting and pushing

`registerGoals` registers seven goals and five target selectors, with no
inherited golem registrations to precede them:

| Selector | Priority | Goal and direct configuration |
|---|---:|---|
| goal | `1` | Melee Attack, speed `1`, follow when unseen |
| goal | `2` | Move Towards Target, speed `0.9`, range `32` |
| goal | `2` | Move Back To Village, speed `0.6`, not check-no-target, XZ `10`/Y `7` |
| goal | `4` | Golem Random Stroll In Village, speed `0.6` |
| goal | `5` | Offer Flower |
| goal | `7` | Look At Player, range `6` |
| goal | `8` | Random Look Around |
| target | `1` | Defend Village |
| target | `2` | Hurt By, no alerted classes |
| target | `3` | nearest Player, interval `10`, must see, need not reach, selector `isAngryAt` |
| target | `3` | nearest Mob, interval `5`, need not see or reach, selector Enemy-and-not-Creeper |
| target | `4` | Reset Universal Anger, not alerting others |

Both priority-`2` goals and both priority-`3` selectors are distinguished
only by registration order. The Player selector is the neutral-mob anger
predicate, so an Iron Golem never targets a Player merely for being nearby:
it must be the persistent anger target, or `universalAnger` must be enabled
while the golem is angry. The Mob selector accepts every `Enemy` except
Creeper regardless of line of sight.

`canAttack` adds two hard exclusions before the inherited check. A
player-created golem can never attack a Player at all, and no golem can ever
attack a Creeper. The Creeper exclusion is therefore enforced twice — once
in the selector and once in `canAttack`.

`doPush` runs on every collision push. When the pushed entity is an `Enemy`
that is not a Creeper, one `nextInt(20)` is consumed and a result of `0`
sets it as the target directly, bypassing the target selectors and their
sight and range rules. The inherited push then runs. This is the only path
by which an Iron Golem acquires a target from mere contact.

### Village defence and player reputation

`DefendVillageTargetGoal` claims only the `TARGET` flag and uses combat
targeting at range `64`. It inflates the golem box by `(10,8,10)`, collects
every `Villager` and every `Player` inside it, and for each Villager/Player
pair reads that Villager's reputation for that Player. A reputation at or
below `-100` records the Player as the potential target; later pairs
overwrite earlier ones, so the last matching Player in enumeration order
wins.

Admission then rejects a Spectator or Creative Player. On start the goal
assigns the target directly and runs the inherited target start. Reputation
storage, gossip decay and the events that lower reputation retain their own
owners.

### Village movement and strolling

`MoveBackToVillageGoal` is a Random-Stroll subclass with XZ distance `10`
and Y distance `7`, constructed with speed `0.6` and check-no-target
`false`, so it can run while the golem has a target. Its admission and
destination search resolve village points through the server level.
`GolemRandomStrollInVillageGoal` provides the ordinary in-village wander at
speed `0.6`. Both retain `MOB-AI-001` for pathing.

### Offering a Poppy

`OfferFlowerGoal` claims Move and Look. Admission requires all three of:

1. the level reports bright outside;
2. one `nextInt(8000)` draw returns exactly `0`; and
3. a nearest entity in the `candidate_for_iron_golem_gift` tag exists within
   the golem box inflated by `(6,2,6)` under non-combat targeting at range
   `6`.

The locked tag contains `minecraft:villager` plus the nested
`accepts_iron_golem_gift` tag, which contains exactly
`minecraft:copper_golem`. The Iron Golem is in neither, so it can never
select another Iron Golem.

Start stores `adjustedTickDelay(400)` and calls `offerFlower(true)`.
Because the goal does not require every-tick updates, the nominal `400`
becomes `200` goal advances under the alternate-phase selector. Each tick
looks at the stored entity with limits `30/30` and predecrements the
counter. Continuation requires a strictly positive counter.

Stop always calls `offerFlower(false)` first. Then, only when the counter
reached exactly `0` — that is, the offer ran to completion rather than being
interrupted — and the stored entity is a `Mob` in `accepts_iron_golem_gift`
whose antenna slot is empty and whose box still intersects the inflated
golem box, the goal places a default Poppy in that Mob's antenna slot and
marks the slot a guaranteed drop. The stored entity reference is then
cleared.

`offerFlower(true)` sets the counter to `400` and broadcasts entity event
`11`; `offerFlower(false)` sets it to `0` and broadcasts event `34`. On the
client, event `11` sets the counter to `400` and event `34` clears it, so
the visible flower duration is driven entirely by those two events and not
by a metadata field.

### Melee attack, knockback and repair

`doHurtTarget` sets the attack-animation counter to `10` and broadcasts
entity event `4` before computing damage. With `f` the current attack-damage
attribute value, the dealt amount is

- `f/2 + nextInt((int)f)` when `(int)f > 0`; and
- `f` otherwise.

At the default attribute `15` this is `7.5 + nextInt(15)`, i.e. `7.5` to
`21.5` in whole steps. The source is an ordinary mob attack.

On a successful hit against a `LivingEntity`, the golem adds
`(0, 0.4*max(0, 1-knockbackResistance), 0)` to the victim's velocity — a
pure vertical launch independent of direction, scaled down by the victim's
own knockback resistance — and then runs enchantment post-attack effects.
A non-living victim uses knockback resistance `0` and still receives the
full vertical component. The Iron Golem Attack sound plays at `1/1`
regardless of whether the damage succeeded.

Client event `4` independently sets the attack counter to `10` and plays the
same sound, so the swing and its sound are visible even when the server
damage is rejected.

`hurtServer` samples the crack level before delegating and, when the hit is
accepted and the level changed, plays Iron Golem Damage at `1/1`.
`getCrackiness` maps `health/maxHealth` through the `GOLEM` thresholds
`0.75/0.5/0.25` to `NONE`, `LOW`, `MEDIUM`, `HIGH`.

`mobInteract` accepts only an Iron Ingot. It records health, heals `25`,
and returns `PASS` when the health did not change — so a golem already at
`100` consumes nothing. Otherwise it plays Iron Golem Repair at volume `1`
and pitch `1 + (nextFloat - nextFloat)*0.2`, consumes one ingot from the
stack, and returns `SUCCESS`. The two `nextFloat` draws are always consumed
in that order.

`playStepSound` plays Iron Golem Step at `1/1` for every step, ignoring the
block argument. `AbstractGolem` returns `null` for ambient, hurt and death
sounds and sets ambient interval `120`; Iron Golem overrides only hurt and
death, so it still has no ambient sound and the interval is inert.

`getLeashOffset` is `(0, 0.875*eyeHeight, width*0.4)`.

### Construction from Carved Pumpkin

`CarvedPumpkinBlock.onPlace` runs whenever the placed state's block differs
from the previous one, and tries Snow Golem, then Iron Golem, then Copper
Golem in that fixed order. The Iron-Golem full pattern is one layer, three
rows tall and three wide:

```
~^~
###
~#~
```

`^` accepts Carved Pumpkin or Jack o'Lantern, `#` requires exactly
`minecraft:iron_block`, and `~` requires air. The separate base pattern used
by `canSpawnGolem` replaces the top row with `~ ~`, leaving the pumpkin cell
unconstrained.

On a match the block creates the entity with reason `TRIGGERED`, sets
player-created `true`, and hands the pattern position `(1,2,0)` — the
bottom-centre Iron Block — to the shared spawn routine. That routine clears
every matched pattern block to Air first, snaps the entity to
`(x+0.5, y+0.05, z+0.5)` at yaw/pitch `0/0`, adds it, fires the
summoned-entity criterion for every `ServerPlayer` within the entity box
inflated by `5`, and finally re-updates the cleared pattern blocks.

Because the pumpkin is cleared before the entity is added, a failed
insertion still destroys the structure. A null creation aborts before any
block is cleared and falls through to the Copper-Golem attempt.

### Village summoning

`Villager.spawnGolemIfNeeded(level, gameTime, 5)` runs from the gossip
path. It first requires `wantsToSpawnGolem`, which is the conjunction of

- a `LAST_SLEPT` memory within the last `24000` ticks; and
- no `GOLEM_DETECTED_RECENTLY` memory.

It then collects every Villager in its own box inflated by `(10,10,10)`,
filters that list by the same `wantsToSpawnGolem` predicate, limits it to
`5`, and returns when fewer than `5` remain. `GolemSensor` scans every
`200` ticks, sets `GOLEM_DETECTED_RECENTLY` for `599` ticks when any
`NEAREST_LIVING_ENTITIES` entry is an Iron Golem, and is the only writer of
that memory besides the post-spawn sweep.

The spawn itself is `SpawnUtil.trySpawnMob` with reason `MOB_SUMMONED`,
`10` attempts, horizontal spread `10`, vertical scan `8` and the
`LEGACY_IRON_GOLEM` strategy, with the collision check disabled.

Each attempt picks independent inclusive `-10..10` X and Z offsets around
the Villager's block position and starts at `y+8`. The vertical scan walks
down through `8` steps, and at each step accepts the position when the
strategy's `canSpawnOn` holds for the candidate and the state above it.
`LEGACY_IRON_GOLEM` rejects the candidate outright when it is Cobweb,
Cactus, Glass Pane, any Stained Glass Pane, any Stained Glass, any Leaves,
Conduit, Ice, TNT, Glowstone, Beacon, Sea Lantern, Frosted Ice, Tinted Glass
or Glass; otherwise it requires the state above to be air or liquid and the
candidate itself to be solid or Powder Snow. On success the position moves
one block up.

Because the collision flag is `false`, no bounding-box test runs at this
stage. The created mob must still pass `checkSpawnRules` and the golem's own
`checkSpawnObstruction`; failure discards it and the loop continues. On the
first success the golem is added with passengers and `playAmbientSound` runs
as a no-op, and every Villager in the original unfiltered list — not just
the five that voted — receives `GOLEM_DETECTED_RECENTLY`. A completely
failed set of attempts leaves every memory untouched, so the villagers retry
on the next gossip tick.

`checkSpawnObstruction` requires the block below to be stand-on-able, then
requires all three blocks at `y+1`, `y+2` and `y+3` to be valid empty spawn
blocks for the type, then requires the golem's own block to be a valid empty
spawn block against an empty fluid state and the level to report the entity
unobstructed.

### Placement, structures and other producers

The separate placement registration is `ON_GROUND` with heightmap
`MOTION_BLOCKING_NO_LEAVES` and the generic `Mob.checkMobSpawnRules`
predicate. All `66` locked baseline biomes contain zero Iron Golem spawn
rows, so that registration serves only spawner, command and custom paths.

Exactly two of the `1,212` locked templates carry an exact
`minecraft:iron_golem` entity identity:

- `village/common/iron_golem`, a `1×3×1` element holding one golem at
  `(0,1,0)` with `PersistenceRequired=1` and `PlayerCreated=0`, reachable
  through the single-element `village/common/iron_golem` pool; and
- `pillager_outpost/feature_cage1`, a `7×4×7` element holding one golem at
  `(3,1,3)` with `PersistenceRequired=0` and `PlayerCreated=0`.

Every village town-centre template references the pool name rather than the
entity, so the village golem is produced through jigsaw pool resolution and
not by a direct template entity in those pieces.

The Spawn Egg is raw/protocol item ID `1197`, common, maximum stack `64`,
and its `entity_data.id` is `minecraft:iron_golem`. Egg-spawned golems are
not player-created.

### Loot, tags, advancements and cross-entity joins

The entity loot table uses random sequence `minecraft:entities/iron_golem`
and evaluates two ordered one-roll pools, both unconditional:

1. Poppy, item protocol ID `260`, integer-uniform count `0..2`; and
2. Iron Ingot, item protocol ID `932`, integer-uniform count `3..5`.

Neither pool is gated on a player kill, Looting or fire, and the XP reward
is `0`. Positive-count filtering, mob-loot gamerule, equipment drops and
death ordering retain their cited owners. A golem that completed a Poppy
offer additionally guarantees the Poppy drop from the recipient's antenna
slot, which is that recipient's own drop, not the golem's.

Exactly one direct entity-type tag names the Iron Golem:
`fall_damage_immune`. It is in neither `candidate_for_iron_golem_gift` nor
`accepts_iron_golem_gift`, so an Iron Golem is never a gift candidate and
one Iron Golem never gifts another. Those two tags describe recipients:
`candidate_for_iron_golem_gift` holds `minecraft:villager` plus the nested
`accepts_iron_golem_gift`, which holds exactly `minecraft:copper_golem`.

One advancement names it. `adventure/summon_iron_golem` has the single
required criterion `summoned_golem`, a `summoned_entity` trigger whose
predicate is exactly `minecraft:iron_golem`, with parent `adventure/trade`,
frame `goal`, Carved Pumpkin icon and telemetry enabled. Only the shared
pumpkin spawn routine fires that trigger, so a Villager-summoned, template,
Egg or command golem never completes it.

Three other subsystems name the identity directly: `Raider` resets its
inactivity counter when its target is a Player or an Iron Golem during an
active raid; `Breeze` treats Player and Iron Golem alike in its own target
predicate; and `GolemSensor` detects only this exact type.

### Migration and schema closure

Six exact migration/schema contexts name the Iron Golem family:

- `EntityIdFix` maps legacy `VillagerGolem` to
  `minecraft:villager_golem`;
- `EntityTheRenameningFix` maps `minecraft:villager_golem` to
  `minecraft:iron_golem`;
- schema `V705` registers the legacy `minecraft:villager_golem` entity
  shape;
- schema `V1460` registers the same legacy shape for its own generation;
- schema `V1510` moves the legacy shape to the current name; and
- `ItemStackSpawnEggFix` maps `minecraft:iron_golem` to
  `minecraft:iron_golem_spawn_egg`.

`EntityUUIDFix` additionally includes the current identity in its Mob UUID
rewrite set. Generic entity, equipment, effect and anger fields retain
their schema owners.

**Branches and aborts:**

- `canAttack` rejects Players for player-created golems and Creepers for
  every golem, before the inherited alliance and team rules.
- The Player target selector admits only through neutral-mob anger; the Mob
  selector admits every non-Creeper `Enemy` without a sight test.
- Village defence aborts with no qualifying Villager/Player pair and rejects
  Spectator and Creative Players after selection.
- The flower offer aborts on darkness, on any of the `7999` non-zero
  `nextInt(8000)` results, or with no tagged candidate in range; its gift
  step additionally aborts on interruption, a non-`Mob` candidate, a missing
  tag, an occupied antenna slot or a box that no longer intersects.
- Iron-Ingot interaction returns `PASS` for any other item and for a golem
  already at full health, consuming nothing.
- Construction aborts when the Snow-Golem pattern matched first, when the
  Iron-Golem pattern does not match, or when creation returns null; a null
  creation leaves the blocks intact.
- Village summoning aborts on the sleep/detection gate, on fewer than five
  voting Villagers, or on ten failed placement attempts; only the last case
  leaves the detection memory unset.
- Distance despawn never applies.

**Invariants:**

- An Iron Golem never despawns for distance, on any category or persistence
  state.
- Slot `16` bit `0x01` is the only synchronized golem state and mirrors
  persisted `PlayerCreated`.
- Only the Carved-Pumpkin path sets player-created `true`; Villager,
  template, Egg and command golems are all village-behaving.
- A player-created golem cannot target a Player through any path.
- No golem can ever target a Creeper.
- Attack knockback is purely vertical and independent of attack direction.
- The crack overlay is a pure function of the health fraction, not of damage
  history.
- Loot is unconditional: `0..2` Poppies and `3..5` Iron Ingots, with `0` XP.
- `fall_damage_immune` is the only entity-type tag that names the golem.
- Exactly one advancement names the golem and only pumpkin construction can
  award it.

**Boundary cases and quirks:**

An Iron Golem is unaffected by Peaceful and never despawns, so a single
summoned golem persists indefinitely. A pumpkin-built golem is permanently
unable to attack Players even after the builder is gone, while an
otherwise identical Villager-summoned golem is not. Colliding with a hostile
mob can hand the golem a target it could never have selected, because the
push path skips sight and range. Village defence picks the last qualifying
Player in enumeration order rather than the worst-reputed one. The Poppy
gift only lands when the full offer runs to completion, so interrupting the
goal shows the flower without ever handing it over, and the recipient must
be a Copper Golem because no other type is in the accepting tag. The repair
interaction silently does nothing at full health but still returns `PASS`
rather than consuming the ingot. Construction clears the pattern before
inserting, so a rejected insertion destroys the iron and pumpkin anyway.
Villager summoning disables its collision check, so the golem can be created
inside geometry that only the later obstruction test rejects. The
summoned-entity advancement is reachable only through pumpkin construction,
never through the village path it describes. Only two locked templates carry
the identity, and one of them is a Pillager Outpost cage rather than a
village.

**Failure semantics:**

A failed melee hit still plays the attack sound, broadcasts the swing event
and applies no knockback. A rejected effect or damage result is not rolled
back. Failed pumpkin insertion leaves the pattern cleared. A completely
failed village summon leaves every brain memory unchanged and retries later.
A discarded spawn attempt inside `SpawnUtil` leaves no partial entity. A
